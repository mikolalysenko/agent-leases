# Security model

This prototype bounds requests made by a Linux worker that the trusted operator launches through `lease run`. It does not make generated code safe, establish the truth of its output, or isolate a worker already running with host access. The gateway is a credential-holding trusted component.

## Required deployment conditions

- Use a disposable GitHub repository with Actions disabled and no privileged integrations. Draft PRs are not an execution barrier. The gateway does **not** inspect or enforce the repository's automation configuration.
- Launch the entire worker through `lease run` on Linux with bubblewrap. The CLI refuses unsupported platforms instead of falling back to host execution. macOS supports only development of the gateway/client and tests, not worker isolation.
- Keep state and credential files outside the worker workspace. Use a dedicated operator account or machine for a stronger deployment boundary. Do not run the gateway as root. Installation tokens never go in worker environment variables or files.
- Supply an empty, private workspace or inspect all its content. The launcher rejects symlinks, hard links, sockets, devices, and FIFOs already in it. This is a launch-time check: no other host process may add mounts or files during launch or expose sensitive sockets there afterward. Ordinary files can still contain secrets; this check does not recognize secret data.
- Treat `/usr`, `/bin`, `/sbin`, `/lib`, `/lib64`, the Python package, the kernel, and bubblewrap as trusted system content. They are mounted read-only. Do not put credentials or service sockets in these system directories. The launcher is not a micro-VM or a minimal immutable runtime image.
- Keep the host clock and authority DB trustworthy. Never roll back a live lease DB or reuse stale backups as active authority. Do not share one socket among workers that need independent budgets.

## What the worker can do

The worker can execute arbitrary available commands, change files in its workspace, and use the four named GitHub operations within its budgets. It may disclose any readable input through an authorized publish, PR body, or comment. Nothing inspects whether a change actually advances `purpose`. The operator is approving authority, not approving the truth or quality of future work.

The launcher uses mount, PID, IPC, UTS, and network namespaces, a fresh home and temporary directory, a cleared environment, dropped capabilities, a new session, and closed inherited file descriptors. It binds only the per-lease socket from the authority directory. Host network routes, DNS configuration, home directory, credential stores, state, and other host sockets are not deliberately exposed. Stdout/stderr and workspace files are intentional output channels to the trusted operator. Stdin is detached.

This configuration still shares the host kernel. There is no dedicated seccomp profile, CPU/memory/process/disk quota, runtime image attestation, or complete sandbox-escape test corpus. Resource exhaustion, kernel vulnerabilities, malicious system tools, and a compromised gateway or operator are outside its guarantee.

## What is enforced

| Attempt | Result |
| --- | --- |
| Choose a different repo, URL, API method, token, base, or draft state | Unknown field/operation denied before dispatch |
| Force-push, overwrite a branch, merge, review, approve, delete, release, upload | No operation exists |
| Publish outside the lease branch prefix | Branch name is generated by the gateway |
| Open a PR from somebody else's branch | Requires persisted successful branch ownership |
| Comment on somebody else's PR | Requires persisted successful PR creation by this lease |
| Race requests for the last budget unit | Transactional reservation admits at most the remaining capacity |
| Replay a request ID after a lost response | Recorded result; no new dispatch |
| Change payload under the same ID | Conflict |
| Retry an ambiguous upstream write | Same ID returns uncertainty; reservation stays consumed |
| Extend via the worker socket | No administrative operation exists |
| Continue after revocation/expiry | New dispatch authorizations denied; already-dispatched work may finish |
| Bypass the gateway with raw DNS/TCP/UDP/IPv6 | No host network in the Linux worker namespace |
| Obtain credentials from the gateway | No credential-returning operation; responses use a closed result schema |

These claims assume the deployment conditions above. An unsandboxed host process can of course bypass this gateway using its own network and credentials.

## Remaining risks

**Authorized disclosure and external effects.** Caps limit attempts, not the value of data in each attempt. PR notifications, webhooks, remote automation, and future consumption of the published code are not metered. A single publish creates multiple remote Git objects. The `payload_bytes` cap is a defined input measure, not a transport-byte guarantee.

**Remote changes and aliases.** The policy binds a repository by owner/name, not immutable repository ID. Operators must not rename/transfer/reassign it during a lease. Other authorized actors can change the base or a created branch. This gateway does not prevent their actions or revalidate an approved SHA against remote branch history.

**Uncertainty.** After a timeout/crash there can be a remote branch or PR the gateway cannot safely claim ownership of. A person must reconcile it. Pending work burns budget even if it never reached GitHub. There is no exactly-once guarantee, automatic refund, or queue that resumes on grant.

**Local persistence.** The private DB includes replayable read results. The hash chain is locally verifiable, not immutable or remotely anchored. A full disk or unavailable DB denies work; a disk failure after an upstream effect can still lose the completion record. Restore procedures are not automated.

**Availability.** Eight connection slots and body/response limits reduce basic connection abuse. A worker can still spam denials/status, fill audit storage, monopolize operations, or exhaust local resources. This is a single-operator prototype, not a multi-tenant service.

**Provider credentials.** App tokens are narrowly minted, but the App's private key remains powerful and must be isolated. Token-file mode cannot prove the operator supplied a narrow token. Local revocation does not revoke that external credential; it only stops this gateway from issuing new dispatch authorizations.

**Provenance.** Commit/PR/comment stamps are human-readable attribution, not signatures. No taint or trusted-input claim is inferred from them. A local audit hash does not make a public stamp authentic.

## Verification strategy

Tests exercise the state machine at both the gateway and SQLite concurrency boundaries. A recording provider checks the exact GitHub paths, permissions, branch names, draft flag, and ownership relationships. Failures are injected after upstream writes and between publish steps. The HTTPS transport is checked for fixed-host behavior, no redirect following, and no retries. Broker JWT signatures are verified with OpenSSL.

Linux CI launches an actual worker with canary host files/environment and attempts direct TCP, UDP, IPv6, and DNS access, socket administration, and an alternate workspace socket. This establishes the tested boundary on that runner; it is not a proof against every kernel or sandbox bypass.

Do not put real credentials in test fixtures or CI secrets. Tests and the offline demo need none.
